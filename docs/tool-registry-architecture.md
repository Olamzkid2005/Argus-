# Tool Registry Architecture

> **Last updated:** 2026-07-25
> **Covers:** Python worker tool registry (4 layers) + TypeScript planner tool registry

---

## Overview

Argus has **two independent tool registries** — one on the Python side (workers) and one on the TypeScript side (planner). This separation is intentional: different schema, different purpose, different lifecycle.

| Registry | Location | Purpose |
|----------|----------|---------|
| **Python** | `argus-workers/tool_definitions.py` | Execution metadata (phases, params, commands, timeouts, signal quality) |
| **TypeScript** | `Argus-Tui/packages/opencode/src/argus/workflows/tool-registry.ts` | Planning metadata (capabilities, scoring, consumes/provides, auth gating) |

## Python Architecture — 4 Layers

```
┌─────────────────────────────────────────────────────────────────┐
│  Layer 1: YAML Source of Truth                                  │
│  tools/definitions/*.yaml (67 files)                            │
│                                                                 │
│  Each file defines a tool's name, command, args, parameters,    │
│  timeout, signal_quality, and optional requires gate.           │
│  Cross-language: both Python and TypeScript can read this.      │
├─────────────────────────────────────────────────────────────────┤
│                         │ generates                             │
│                         ▼                                       │
│  Layer 2: Auto-Generated Python                                 │
│  _generated_tools.py (1,155 lines, 67 tools)                    │
│                                                                 │
│  Generated by: scripts/generate_tool_defs.py                    │
│  Header: "Auto-generated tool registrations — DO NOT EDIT"      │
│  Imports ToolDefinition from tool_definitions.py                │
│  Calls _register() for each YAML-defined tool.                  │
├─────────────────────────────────────────────────────────────────┤
│                         │ imported via `from _generated_tools import *`
│                         ▼                                       │
│  Layer 3: Declarative Registry (Single Source of Truth)         │
│  tool_definitions.py (~1,650 lines)                             │
│                                                                 │
│  Contains:                                                      │
│  • ToolDefinition, ToolParameter, ToolRequires dataclasses      │
│  • SignalQuality enum (CONFIRMED, PROBABLE, CANDIDATE)          │
│  • TOOLS dict — the canonical registry                         │
│  • ~60 _register() calls that can OVERRIDE generated defs       │
│  • Helper functions: get_tools_for_phase, evaluate_gate, etc.   │
│  • build_mcp_tool_definitions() → bridges to Layer 4            │
├─────────────────────────────────────────────────────────────────┤
│                         │ build_mcp_tool_definitions()           │
│                         ▼                                       │
│  Layer 4: Runtime MCP Server Representation                     │
│  mcp_server.py:ToolDefinition (+ ToolSchema, MCPToolResult)     │
│                                                                 │
│  Separate class from Layer 3's ToolDefinition:                  │
│  • Has additional EXECUTION fields: command, args, timeout,     │
│    env, binary (for subprocess execution)                       │
│  • Has planner fields: capabilities, credential_roles           │
│  • Loaded by MCPServer which also loads YAML directly at        │
│    startup via _load_yaml_tools() for standalone use.           │
└─────────────────────────────────────────────────────────────────┘
```

### Layer Details

#### Layer 1 — YAML Definitions

**Location:** `argus-workers/tools/definitions/*.yaml` (67 files)

Each YAML file defines a tool:

```yaml
name: nuclei
command: nuclei
args:
  - "-json"
  - "-silent"
description: Vulnerability scanner based on YAML templates
parameters:
  - name: target
    flag: "-u"
    type: string
    required: true
    description: Target URL
timeout: 600
signal_quality: confirmed
requires:
  target_scheme: "https"
```

**CI validation:** `.github/workflows/lint.yml` -> `yaml-lint` job validates all YAML files are parseable. `tool-defs-check` job verifies `_generated_tools.py` is in sync.

#### Layer 2 — Auto-Generated Python

**Location:** `argus-workers/_generated_tools.py` (1,155 lines, 67 tools)
**Generator:** `argus-workers/scripts/generate_tool_defs.py`

Key invariant: **NEVER edit `_generated_tools.py` by hand.** Regenerate it:

```bash
cd argus-workers
python scripts/generate_tool_defs.py           # write _generated_tools.py
python scripts/generate_tool_defs.py --check   # CI mode — verify no drift
```

The generator reads all YAML files, parses them with `yaml.safe_load()`, and emits Python `_register(ToolDefinition(...))` calls. The output has a SHA-256 fingerprint to detect uncommitted changes.

**CI check:** `.github/workflows/lint.yml` runs `python scripts/generate_tool_defs.py --check` in the `tool-defs-check` job to detect drift between YAML and generated Python.

#### Layer 3 — Declarative Registry (SSOT)

**Location:** `argus-workers/tool_definitions.py` (~1,650 lines)

**Core data types:**

```python
@final
@dataclass(frozen=True)
class ToolDefinition:
    name: str                          # Unique tool name
    description: str                   # Human-readable description
    phases: list[PhaseName]            # Which phases this tool belongs to
    binary: str | None = None          # Binary name on PATH (defaults to name)
    default_args: list[str] = []       # Default CLI arguments
    parameters: list[ToolParameter]    # Parameter schemas
    timeout: int = 300                 # Execution timeout in seconds
    signal_quality: SignalQuality      # Findings reliability tier
    requires: ToolRequires | None      # Activation gate
    priority: int | None               # Tool selection priority
    cost: str | None                   # Cost tier (low, medium, high)
    risk_level: str | None             # Execution risk
    exploit_categories: list[str]      # Vulnerability types covered
    # ... 20+ fields total
```

**`_register()` pattern:** Generated tools load FIRST, then inline definitions can OVERRIDE them:

```python
# Line 209: Import all YAML-generated definitions
from _generated_tools import *  # noqa: F403,E402

# Lines 211+: Inline overrides — these run AFTER the import above,
# so they can replace any generated definition with richer metadata.
_register(
    ToolDefinition(
        name="pip-audit",  # Overrides _generated_tools.py definition
        description="Python dependency vulnerability scanner (overrides _generated_tools.py)",
        phases=["repo_scan"],
        ...
    )
)
```

**Why override?** The YAML definitions are minimal (name, command, args, timeout, signal_quality). The inline overrides add richer metadata: parameter schemas, `requires` gates, `risk_level`, `exploit_categories`, `cost`, and `priority`. Not all tools need overrides — only those that benefit from the additional metadata.

**`evaluate_gate()` — runtime gate checking:**

```python
def evaluate_gate(tool_name: str, recon_context) -> bool:
    """Check if a tool's requires gate is satisfied.
    
    Checks:
    1. tech_contains — target's tech stack must include listed technologies
    2. recon_signals — boolean signals from ReconContext must be truthy
    3. target_scheme — target URL must start with the required scheme
    """
```

**`build_mcp_tool_definitions()` — bridge to Layer 4:**

```python
def build_mcp_tool_definitions() -> list:
    """Convert Layer 3 ToolDefinitions to Layer 4 MCP ToolDefinition format.
    
    Maps fields across the two class schemas:
      Layer 3 → Layer 4
      tool.binary or tool.name → command
      tool.default_args → args
      tool.parameters → ToolSchema list
      tool.signal_quality.value → signal_quality (string)
    """
```

#### Layer 4 — Runtime MCP Server

**Location:** `argus-workers/mcp_server.py:ToolDefinition`

This is a SEPARATE class from `tool_definitions.py:ToolDefinition`. They have diverged intentionally:

| Field | Layer 3 (declarative) | Layer 4 (runtime) |
|-------|----------------------|-------------------|
| Execution | `default_args`, `binary` | `command`, `args`, `env` |
| Planning | `phases`, `parallel_safe` | `capabilities`, `credential_roles` |
| Reliability | `signal_quality` (enum) | `signal_quality` (string) |
| Parameters | `ToolParameter` (dataclass) | `ToolSchema` (JSON schema) |

**`MCPServer`** also loads YAML directly at startup via `_load_yaml_tools()` for environments where `tool_definitions.py` Layer 3 isn't available.

## Design Decisions

### Decision 3.3b — Separate Concerns (Confirmed)

From Workstream 3 (Tool-Registry Resolution):

> `tool_definitions.py` = declarative registry (phases, parameters, signal_quality)
> `mcp_server.ToolDefinition` = runtime (command, args, timeout, env)
>
> No deduplication needed. The two classes serve different purposes and have
> different consumers. Keeping them separate avoids coupling the declarative
> tool metadata to the execution runtime.

### Why Two Registries (Python + TypeScript)?

The Python registry focuses on **execution** — how to run a tool, how long it takes, what parameters it needs, and how reliable its findings are.

The TypeScript registry focuses on **planning** — what capabilities a tool satisfies, what score it has for each capability, what auth gating it needs, and what other capabilities it depends on.

The YAML files in `tools/definitions/` serve as a common starting point for both, but each side enriches the data independently.

### Override Pattern

Not all tools need YAML → inline override. The override pattern is used for:

1. **Adding parameter schemas** — tools like `nuclei`, `dalfox`, `sqlmap` have full parameter definitions
2. **Adding `requires` gates** — tools like `jwt_tool`, `wpscan`, `bandit` have conditional activation
3. **Fixing auto-generated errors** — `playwright-xss`, `playwright-bola`, `playwright-privesc` had incorrect `target_scheme` list-literal strings
4. **Adding risk/cost metadata** — post-exploitation tools have `risk_level="high"`

### `_AGENT_INTERNAL_TOOLS`

Tools that are implemented as Python functions (not external binaries) are listed in `_AGENT_INTERNAL_TOOLS`. These always return `True` from `is_tool_available()` because they have no external binary dependency.

Current set (21 tools): `register`, `login`, `post_exploitation`, `credential_replay`, `internal_probe`, `cloud_metadata_probe`, `ai_surface_detected`, and the 14 advanced security tools (finding_correlation_engine, attack_path_generator, etc.).

## Adding a New Tool

```python
# 1. Create YAML definition
# tools/definitions/my-tool.yaml
# name: my-tool
# command: my-tool
# ...
# 
# 2. Regenerate Python
# cd argus-workers && python scripts/generate_tool_defs.py
#
# 3. (Optional) Add inline override with richer metadata
# In tool_definitions.py:
# _register(ToolDefinition(
#     name="my-tool",
#     description="...",
#     phases=["scan"],
#     parameters=[ToolParameter(...)],
#     timeout=300,
#     signal_quality=SignalQuality.CANDIDATE,
# ))
#
# 4. (If TypeScript planner needs it) Update tool-definitions.yaml
```
